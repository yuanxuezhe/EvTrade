# 全局规范 — 知识库与代码同步铁律

> **本文件是整个项目的最高工作准则。任何需求、BUG 修复、重构，都必须先读本文件并严格遵守。**
>

---

## 一、知识库定位

`知识库/` 目录是项目的**唯一事实来源（Single Source of Truth）**。

- 每个知识库文档 ↔ 一组代码文件，一一对应、互相锚定
- 知识库描述"这个模块是什么、怎么实现的、改它要注意什么"
- 代码是知识库描述的执行结果
- **知识库过时 = 代码不可信**。发现不一致，当场修正知识库

## 二、修改流程（强约束，顺序不可颠倒）

```text
第一步：定位知识库
    根据改动需求，在 知识库/ 中找到对应模块文档
    读文档，确认实现逻辑、影响面、注意事项

第二步：先改知识库
    把"要怎么改"先写进知识库文档
    （新逻辑描述、新增字段、新增接口、新增页面等）
    涉及多个模块时，每个模块的知识库文档都要改

第三步：再改代码
    按知识库中已更新的描述，修改对应代码文件
    代码路径必须与知识库文档中的「对应代码路径」章节一致

第四步：改测试（只测涉及的）
    只为本次改动的模块写/改测试
    跑测试时只跑涉及模块的测试文件，不跑全量

第五步：同步收尾
    git diff --stat 检查改动范围是否最小化
    知识库改动 + 代码改动 + 测试改动 可以合并提交
```

## 三、改动范围铁律（Scope Control）

### 3.1 禁止事项

| 禁止 | 说明 |
|------|------|
| ❌ 大面积无关重构 | 改 A 模块时顺手"优化" B 模块 |
| ❌ 全量跑测试 | 只跑涉及模块的测试（见 3.3） |
| ❌ 改知识库不对应的代码 | 知识库里没有描述的模块不要动 |
| ❌ 改代码不更新知识库 | 代码改了知识库不改 = 同步断裂 |
| ❌ 一次性跨多模块大改 | 需要跨模块时拆成多次小改动 |
| ❌ 注释/文档里写历史版本标注 | 禁止 "v123"、"2026-08-xx 改动" 这类叙事（见第六条） |

### 3.2 改动范围判定方法

```text
问自己三个问题：
1. 本次需求涉及哪些知识库文档？（列出文档路径）
2. 这些文档中「对应代码路径」列出了哪些文件？（这些文件才可改）
3. 上述文件的改动会破坏哪些现有测试？（这些测试才需要跑）

答案之外的一切文件，一律不碰。
```

### 3.3 测试范围控制

| 改动类型 | 必跑测试 | 禁跑 |
|----------|----------|------|
| 后端某 API 模块（如 orders） | `pytest server/tests/test_orders*.py` | 其他模块测试 |
| 数据表结构（tables/） | 相关表的测试 + 引用该表的 API 测试 | 全量 |
| 前端某页面（如 T0Trade） | 该页面对应的测试（如有） | 全量 |
| strategy_exec 服务 | `pytest strategy_exec/tests/` 内相关文件 | EvTrade 主服务测试 |
| WebSocket 推送 | `pytest server/tests/test_ws*.py` | 其他 |
| 纯知识库/文档改动 | 无需跑测试 | — |

**验证回归最低集**（改动完成后想确认整体没坏）：
```bash
pytest server/tests/ -x -q --timeout=60   # 仅在后端核心逻辑改动时执行
```

## 四、知识库文件规范

### 4.1 目录与命名

- 目录名、文件名一律**中文**，直观反映模块
- 代码路径、函数名、变量名保留英文原文
- 层级结构：`知识库/<大域>/<模块>/<子功能>.md`

### 4.2 单文件大小

- 单个 md 文件**不超过 300 行**
- 超过就按子功能拆分成多个文件
- 宁可文件多而小，不要文件少而大

### 4.3 每个文档必含的固定章节

```markdown
# <模块名>

## 对应代码路径
`实际代码路径`（相对项目根目录）

## 功能概述
一段话说清这个模块干什么

## 文件清单
| 代码文件 | 作用 |
|----------|------|
| `xxx.py` | 说明 |

## 核心实现
### <子功能>
详细描述：数据流、关键函数、状态流转、协议格式

## 依赖关系
- 上游：依赖哪些模块
- 下游：被哪些模块依赖

## 修改指南
改这里要注意什么、牵一发动全身的点、测试怎么跑
```

### 4.4 与 openspec 的关系

- `openspec/specs/` = **能力级需求规范**（WHAT：要满足什么要求）
- `知识库/` = **实现级事实文档**（HOW：代码怎么实现的）
- 两者互补不冲突：改需求走 openspec change 流程；改实现细节同步知识库
- `docs/` 与 `kb/` 已删除：历史归档内容可通过 git 历史（`git log -- docs kb`）查阅；协议契约见 `openspec/specs/rpc-protocol/` 等能力级 spec

## 六、注释与历史记录规范（禁止版本标注）

**代码注释和知识库只描述"现状"，历史变化一律通过 git 提交记录（中文）承载。**

### 6.1 禁止的写法

```python
# ❌ 错误：版本号叙事
# v118: manual reconcile 不动 positions
# v13 增 raw_id = orig.order_no（结构化冗余）
# 2026-08-20 fix: 走 asyncio.to_thread 防 event loop 阻塞
```

### 6.2 正确的写法

```python
# ✅ 正确：现状描述
# manual reconcile 不动 positions（pos_push 已接管）
# raw_id = orig.order_no（结构化冗余字段）
# 走 asyncio.to_thread 防 event loop 阻塞
```

### 6.3 规则要点

- 改代码/知识库时**禁止新增** "vNN"、"vNN.N"、"YYYY-MM-DD 改动/fix" 等历史标注
- 纯历史叙事（"v80.3 迁 tables"）直接删除；有技术实质的去掉版本/日期前缀保留内容
- 例外保留：REQ-xxx 需求编号、openspec change 目录名（作为路径引用）、库名（pydantic v2）、协议版本（UUID v4）、IndexedDB schema 版本号
- **历史追溯入口**：`git log` / `git blame`，提交说明必须用中文写清改了什么、为什么改
- 每次改动按逻辑单元提交，提交说明格式参考：`feat(模块): 摘要` + 变更要点列表
