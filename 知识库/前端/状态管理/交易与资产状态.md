# 交易与资产状态

## 对应代码路径

- `client/src/stores/order.js`（140 行，委托/成交操作层）
- `client/src/stores/position.js`（56 行，持仓 facade）
- `client/src/stores/asset.js`（40 行，资金 facade）
- `client/src/stores/rpc_status.js`（41 行，RPC 通信健康状态）

## 功能概述

v8 单一缓存源架构下，这四个 store 均为「薄」store：真实数据全部在 holdings（见 持仓状态.md），本层只保留操作动作（order）、UI 局部状态（position）、双向桥接（asset）与独立健康面板（rpc_status）。设计目标：

- **order**：不持有 orders/trades，仅提供 createOrder/placeOrder/cancelOrder 三个 action + placing/canceling loading 态；下单成功后把订单 upsert 回 holdings 缓存，保证后续 WS 推送能按 order_no 匹配。
- **position/asset**：computed 透传 holdings 数据，视图层旧代码 `usePositionStore().positions` / `useAssetStore().asset` 无需改动。
- **rpc_status**：唯一数据源是 WS rpc_status 帧与启动 REST 拉取，反映后端到柜台（QMT RPC）的通信健康。

## 核心实现

### order.js — 下单链路

```js
createOrder(orderData):
  placing=true
  → api.createOrder(orderData)          // 拦截器已展平, res = list 数组
  → order = list[0]                     // v8 统一取 list[0]
  → _upsertToHoldings(order)            // holdings.applyOrderPush(order, 'open')
                                        //   含激活日守门 + 防御性 status 重算
  → return order                        // placing=false

placeOrder(orderData):                  // 与 createOrder 等价(后端同一接口)
  → _shouldConfirmBeforeOrder()         // v93 全站下单二次确认
  │    sysconfig 'confirm_before_order' == true 时弹 ElMessageBox.confirm
  │    用户取消 → throw '用户取消下单'
  → createOrder(orderData)

cancelOrder(orderNo, trdDate):
  → api.cancelOrder(orderNo, trdDate)   // v6: 需 order_no + trd_date
  → 乐观更新: holdings.orders 中对应行 status='51'(待撤)
  → 终态等 ord_cfm push 异步改
```

`_shouldConfirmBeforeOrder` 细节：读 `sysconfigApi.get('confirm_before_order')`，60s 内存缓存（`_confirmCache/_confirmCacheAt`）；读取失败默认不弹；兼容 `{cfg_val}|{value}|裸值` 三种返回形态。v8 注释明确：**不暴露 orders/trades getter**，视图必须显式 `useHoldingsStore().orders`，强制单一源。

### position.js — 持仓 facade

- `positions = computed(() => holdings.positions)` 纯透传。
- 自有 state 仅 UI 局部：`selectedStockCode`（详情抽屉选中项）+ `selectedPosition`（按 code 反查的 computed）。
- `fetchPositions()` delegate `holdings.refreshPositions()`；`initPosition(code)` 调 `api.initPosition` 后刷新。

### asset.js — 资金双向桥

```js
const asset = computed({
  get: () => holdings.cachedAsset,
  set: (v) => { holdings.cachedAsset = v },   // CacheAsset.vue 编辑器需要写回
})
const loading = computed(() => holdings.loading)
fetchAsset() → holdings.refreshAsset()
```

v99 起 `cachedAsset` 还会被 WS `asset_update` 帧覆盖（含 v110 available、v114 last_asset 扩展字段）。

### rpc_status.js — RPC 健康

status 语义（来自后端 rpc_health 心跳）：

| 值 | 含义 |
|---|---|
| 0 | RPC 通讯正常 |
| 1 | RPC 通信异常（积压/超时/连接失败） |
| 2 | 通信正常但无有效数据 |

写入路径唯一化：`setFromPayload(data)` 按字段类型逐个赋值并打 `lastUpdatedAt`。调用方两处——ws_dispatch 的 `rpc_status` 帧、AppHeader.onMounted 拉 `/api/asset/rpc-status` 初始化。

## 依赖关系

- order.js → api（createOrder/cancelOrder）、api/sysconfig（confirm_before_order）、holdings（applyOrderPush / orders 乐观更新）。
- position.js → holdings（positions/refreshPositions）、api（initPosition）。
- asset.js → holdings（cachedAsset/loading/refreshAsset），零独立状态。
- rpc_status.js → 无外部依赖（纯被动写入），由 ws_dispatch 与 AppHeader 驱动。
- 视图层（Trade.vue/T0Trade.vue/useT0OrderSubmit）读数据走 holdings，调操作走 order store。

## 修改指南

- **新增交易动作**（改单/一键撤全部等）：加在 order.js，成功后统一走 `holdings.applyOrderPush` 落缓存，不要绕过守门直接改 holdings.orders。
- **改下单确认策略**：入口在 `_shouldConfirmBeforeOrder`；新增类似 sysconfig 开关时沿用 60s 缓存模式，避免每次下单打后端。
- **不要给 position/asset 加独立数据副本**：任何本地复制都会重新引入双源漂移（v8 之前 ws_dispatch 双写曾出过）；需要派生数据用 computed。
- **改 rpc_status 展示**：AppHeader 读 status/message/requestQueueDepth；新增字段在 setFromPayload 里加类型判断即可。
- **乐观更新边界**：cancelOrder 只把非终态（51-56 之外）标 '51'，改动撤单状态码时同步检查这个白名单。
