## 功能概述

data_access/ 封装对共享 MySQL（evtrade 库）的全部访问：db.py 管理 SQLAlchemy engine/session 单例；strategy_script.py 只读策略脚本表；strategy_task.py 读写任务表 + 审计表 + 最优参数回写，所有 UPDATE 走乐观锁（version 字段）防与 EvTrade 主服务写竞争。

## 核心实现

### db.py — engine/session 管理

- `get_engine()`：模块级单例，lazy init。`create_engine(settings.evtrade_db_url, pool_size=5, max_overflow=10, pool_recycle=1800, pool_pre_ping=True)`；`sessionmaker(bind=engine, expire_on_commit=False)`。
- `get_session()`：返新 Session，**caller 负责 close**（项目内普遍 `with get_session() as s:` 借助 Session 上下文管理器自动关闭）。
- `session_scope()`：with 上下文自动 commit/rollback/close（当前代码库实际多用 `get_session()` 直接 with）。
- `health_check()`：`SELECT 1` 连通性检查（bool）。
- 表结构由 `server/schema.yml` + `sync_schema.py` 维护，strategy_exec 仅消费，不建表。

### 乐观锁模式（strategy_task.py 全部写函数共用）

```python
for attempt in range(1, MAX_RETRIES + 1):        # MAX_RETRIES = 3
    with get_session() as session:
        row = SELECT version ... WHERE id = :i
        result = UPDATE strategy_task SET ..., version = version + 1
                 WHERE id = :i AND version = :v
        session.commit()
        if result.rowcount > 0: return True      # 成功
raise OptimisticLockError(...)                    # 3 次仍冲突
```

目的：strategy_exec 引擎线程与 EvTrade signal_consumer 可能同时写同一 task 行。

### strategy_script.py（只读）

规范约束：strategy_exec 对 `strategy_script` 表**只读**（EvTrade 是唯一写方，spec REQ-SE-005）。

- `get_script(user_id, script_id)`：按复合 PK `(user_id, id)` 查，返 `{id, user_id, name, code, params_schema(list), description, status, is_public}` 或 None。`params_schema` 经 `_json_loads` 解析。
- `get_public_script_by_id(script_id)`：按 id + `is_public=1` 跨用户查公开脚本。
- `list_scripts(user_id, include_public=True)`：自己的 + 可选公开的（自己的排前）。

### strategy_task.py — 各函数签名与语义

- `get_task(task_id) -> Optional[dict]`：`SELECT *` 单行；JSON 字段（`params/backtest_result/positions/live_signals/progress/fields`）自动 `json.loads`。`strategy_task` 已删 `best_params` 列。
- `update_task_status(task_id, status, error_msg=None, execution_service="strategy_exec", execution_pid=None, finished_at=None) -> bool`：写 status（pending/running/finished/failed/stopped）；`finished_at = COALESCE(:fa, finished_at)` 只在显式传时覆盖；False = task 不存在。
- `update_task_progress(task_id, progress: dict) -> bool`：整字段覆盖写 progress JSON。
- `append_live_signals(task_id, new_signals: list, max_keep=500) -> bool`：读旧 live_signals → `(旧 + 新)[-500:]` 环形缓冲合并写回（防 JSON 无限膨胀）。
- `write_audit(task_id, stime, trd_date, phase, trigger_type, stock_code="", price=0.0, volume=0, indicators=None, state=None, msg="", order_no="", payload=None) -> int`：INSERT 一条 `strategy_script_audit`（每条回测信号一行审计），返新行 id。indicators/state/payload 序列化为 JSON。
- `get_batch_tasks(strategy_id, batch_no) -> list[dict]`：批次模型 —— 按 `(strategy_id, batch_no)` 读批次内全部 task（id 升序），JSON 字段解析；空 list = 批次不存在。
- `update_strategy_best_params(strategy_id, best_params) -> bool`：`UPDATE strategy SET best_params = :bp WHERE strategy_id = :sid`；True=已更新，False=策略不存在（仅 warning 不抛）。

### stale task 清理（progress > 5min → failed）

设计意图（见 `server/main.py:122-131` 注释）：stale running task 的清理职责已移交 strategy_exec ——「启动时清理 progress 超过 5 分钟没更新的 task → 标 failed」，原 `sweep_stale_running_tasks`（server/strategy/service.py）已删，注释指明新位置应在 `strategy_exec/data_access/strategy_task.py`（Phase 2+ 实施）。

**当前代码现状**：strategy_task.py 中**尚未实现**该清理函数，main.py lifespan 也未调用；EvTrade 侧仅留占位日志。若需该能力，应按注释补 `sweep_stale_running_tasks()`（扫 `status='running'` 且 `updated_at` 超时的行 → `update_task_status(..., "failed", error_msg="stale ...")`）并在服务启动（lifespan）时执行。修改前先确认任务清单 `openspec/changes/2026-08-09-strategy-exec-service/tasks.md` 是否有未完成项。

## 依赖关系

- 上游：`config.py`（DB URL / 池参数）；共享 MySQL evtrade 库。
- 下游：`api/internal.py`、`engines/backtrader/`（backtest/live/sweep）全部状态与结果读写。

## 修改指南

- 新增 task 字段写入：沿用乐观锁模板（读 version → UPDATE WHERE version → 重试 3 次 → OptimisticLockError）；JSON 字段记得在 `get_task`/`get_batch_tasks` 的解析列表中登记。
- `append_live_signals` 的 max_keep=500 与 live.py 的 `LIVE_SIGNAL_BUFFER_MAX=500` 保持一致，改动需两处同步。
- 回测结果大 blob 只写 `backtest_result` 一列；列表展示用轻量列 `backtest_metric_value`（见 backtest.py），勿在 list 查询里 SELECT 大 blob。
- 不要在本层加业务逻辑（状态机规则等），保持纯 SQL 访问；状态语义由引擎层决定。
